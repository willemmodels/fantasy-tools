# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal fantasy football tool with three modules: player **Rankings** (drag-and-drop tiered board), a **Draft Tracker** (snake or auction), and a **Trade Analyzer** (side-by-side comparison + drag-and-drop trade evaluator). Dark theme by default.

Two documents outside `src/` are the product/design source of truth and should be consulted for anything not obvious from the code:
- [INIT.md](INIT.md) — the original feature spec (data model, module requirements, the "Big Baller Startup" auction preset).
- [Design Inspo/fantasy-football-design-spec.md](Design%20Inspo/fantasy-football-design-spec.md) — the visual spec (colors, typography, spacing, per-view layout, empty states) for the base light palette; the app now runs in dark mode by default (the user asked for a dark background), with a `.dark` token override in `globals.css` layered on top of the same system.

## Commands

```bash
npm run dev             # start dev server (Next.js + Turbopack)
npm run build           # production build
npm run lint            # eslint
npm run db:seed         # wipe and re-import real players from nflverse (tsx prisma/seed.ts) — needs network
npm run db:seed:mock    # wipe and regenerate synthetic mock players instead (tsx prisma/seed-mock.ts) — offline fallback
npm run db:add-rookies  # additive-only: insert this year's rookies missing from the DB (tsx prisma/add-rookies.ts) — needs network
npx prisma studio       # browse/edit the SQLite dev.db directly
npx prisma migrate dev --name <name>   # after editing prisma/schema.prisma
npx prisma generate                    # regenerate the client (also runs on migrate)
```

There is no test suite. Verify changes by running `npm run build` and walking the three routes (`/rankings`, `/draft`, `/trade`) in a browser.

## Architecture

**Data flow:** SQLite (`dev.db`) is the only persistence for player data, seeded via `prisma/seed.ts`. The app reads it once through `GET /api/players` (`src/app/api/players/route.ts`), and every page loads the full player list into the client-side `useRankingsStore` via the shared `usePlayers()` hook (`src/lib/use-players.ts`) — the Draft and Trade modules don't fetch independently, they read `players` off the rankings store. Everything else (custom rank order, tiers, notes, draft picks, trade assets) is client state that lives in Zustand stores under `src/store/`, persisted to `localStorage`.

**Seed data is real, not mock.** `prisma/seed.ts` fetches from [nflverse](https://github.com/nflverse/nflverse-data) (a free/public dataset) at seed time and needs network access: active 2026 rosters + real 2025 season stats (joined on `gsis_id`/`player_id`) for names/teams/production, the real 2026 schedule for bye weeks (the week each team doesn't play) and posted sportsbook lines (spread/total → implied points per team, currently only available a few weeks out since books haven't priced the rest of the season), and real contract data. The pool is capped per position (`POSITION_CAPS` in `prisma/seed.ts`) to the top ~330 by real 2025 fantasy points, not every active roster spot — since rookies always have zero 2025 production, this cap alone always sorts every rookie to the bottom of their position and excludes all of them (see `add-rookies.ts` below). `prisma/nflverse.ts` holds the fetch/CSV-parsing helpers (`csv-parse`, since fields like headshot URLs contain unescaped commas that a naive `.split(",")` would break on). The per-row derivation logic (age, proj2026, upside/bust/sos, contract label) that both `seed.ts` and `add-rookies.ts` need lives in `prisma/data-loaders.ts` as `buildPlayerRecord()` — it isn't in `seed.ts` itself because `seed.ts`'s `main()` self-executes on import (it would wipe the DB as a side effect of merely importing it from another script). `prisma/seed-mock.ts` is the old fully-synthetic generator, kept as an offline fallback (`npm run db:seed:mock`).

**`npm run db:add-rookies` (`prisma/add-rookies.ts`) adds this year's rookies without regenerating anyone's `id`.** `Player.id` is `@default(uuid())` (see schema below) with no stable natural key, so `db:seed`'s `deleteMany()` + recreate assigns every player — veterans included — a brand-new random id on every run. That's fine for a from-scratch seed, but catastrophic if the user has already spent time customizing a rankings order in the browser: `useRankingsStore`'s `setPlayers` reconciles by id, so an entirely new id set makes every existing player look "new" and the whole custom order gets rebuilt from scratch, sorted by `proj2026`. `add-rookies.ts` sidesteps this by only ever calling `prisma.player.create()` for roster rows (`years_exp === "0"`, i.e. this year's draft class) whose normalized name isn't already in the DB — it never touches or re-creates an existing row, so existing ids (and therefore existing custom rankings) survive untouched. The newly-inserted rookies then show up as genuinely new ids the next time the app loads `/api/players`, and `setPlayers`'s existing reconciliation (`src/store/use-rankings-store.ts`) automatically appends them to the end of *all four* rankings lists (sorted by `proj2026` among themselves) without moving anything already ranked — no extra code was needed there, since that append-only-for-new-ids behavior already existed. Verified by seeding, custom-ranking the pre-existing 332 players, then running `db:add-rookies` and confirming rank #1 didn't move while the added 222 rookies landed at positions 333+.

**`upside`/`bustRisk`/`sos` prefer the user-supplied FantasyPros export** (`FantasyPros_2026_Draft_ALL_Rankings.csv`, read from the project root, not fetched — `loadFantasyProsRatings()` in `prisma/seed.ts`) — real editorial 1-5 ratings, joined by normalized player name. Only ~330/517 of our pool matches it (its export tops out around 500 players); anyone outside it falls back to this script's own heuristic from real inputs (target share, team offense strength, games, experience) — search "no free real defensive-matchup data source" in `prisma/seed.ts` before changing either formula. There's still no free source for 2026 fantasy point *projections* — `proj2026` stays this script's own estimate. **Contracts are best-effort and frequently wrong** — the free nflverse contracts dataset is stale for recent extensions (verified against several real 2024/2025 deals), so anything that doesn't resolve to a real, non-expired, recently-signed row falls back to an honest `"Rookie deal"` / `"Veteran (contract unlisted)"` label derived from real years-in-league rather than asserting a wrong dollar figure — don't "fix" this by loosening the match, that's what caused the original bug.

**Prisma 7 driver adapter:** this project uses the new `prisma-client` generator (output at `src/generated/prisma`, gitignored) with the `@prisma/adapter-better-sqlite3` driver adapter — plain `new PrismaClient()` with no adapter will throw. See `src/lib/prisma.ts` for the singleton and `prisma/seed.ts` for the seed script's own instance. Both read `DATABASE_URL` from `.env` (`file:./dev.db`, resolved relative to the process cwd, i.e. the project root).

**Custom rank order is the spine of the Rankings module — and there are four entirely independent copies of it, one per `RankingsList`.** `RankingsList` (`src/lib/types.ts`) is `"PPR" | "HALF" | "STD" | "BIG_BALLER"`. `useRankingsStore` (`src/store/use-rankings-store.ts`) keeps `orders`/`tiers`/`tierOf` as `Record<RankingsList, ...>` — four full order/tier sets, plus an `activeList: RankingsList` saying which one `ControlsBar`'s single 4-button selector currently has open. They share nothing: reordering or re-tiering in PPR never touches Half-PPR, Standard, or Big Baller, since a player's correct slot legitimately differs across a 12-team single-QB PPR league, a Half-PPR league, a Standard league, and a 4-team 2QB/20-bench Big Baller draft. `RankingsTable`, `ControlsBar`, `PlayerDetailDrawer`, and the Trade module's `comparison-table.tsx`/`trade-evaluator.tsx` never index `orders`/`tiers`/`tierOf` directly — they go through `useActiveOrder()`/`useActiveTiers()`/`useActiveTierOf()` (also in `use-rankings-store.ts`), which read `orders[activeList]` etc. so they follow the selector automatically. The store's mutating actions (`dragReorder`, `addTier`, `renameTier`, `removeTier`, `setTierForPlayer`) are list-generic — they look up `get().activeList` internally and read/write `get().orders[list]` etc. — so don't add a fourth copy of these actions per list; extend the existing ones. `notes`, `drafted`, `searchQuery`, and `positionFilters` are *not* duplicated — those are per-player facts or UI filters, not a ranking-order concept, so they're shared across all four lists. Within a single list, a tier is still just a contiguous run of players in that list's `order` sharing the same `tierOf[playerId]`; `addTier()` still takes no label and continues the `"Tier N"` sequence per-list (capped at `MAX_TIERS` = 10 each).

**There is no dollar/auction-value column anywhere on the Rankings page, in any of the four lists.** That was tried and explicitly removed — the pool doesn't get auction-priced until it's loaded into the Draft board (see below). Big Baller on Rankings is *only* an alternate rank order/tier list to edit, exactly like PPR/Half/Standard; don't reintroduce per-list $ values on this page.

**Scoring format for point *display* (2025 pts, Proj) is derived from `activeList`, not stored separately.** There's no standalone `scoringFormat` field anymore — `listDisplayFormat(list)` (in `use-rankings-store.ts`) maps `PPR|HALF|STD` straight through and maps `BIG_BALLER` to `PPR` (Big Baller isn't a real scoring format, so its list just displays PPR-scaled points while giving you an independent order to edit). `useDisplayScoringFormat()` wraps that for components. Seed data (`fps2025`, `proj2026`) is generated under a PPR baseline; `src/lib/scoring.ts`'s `displayedHistoricalPoints`/`displayedProjection` rescale those numbers live by the ratio between the raw stat line scored under the selected format vs. under PPR — there's no per-format column in the DB. `ControlsBar`'s list buttons use a `LIST_LABELS` map (`"Half-PPR"`, `"Standard"`, `"Big Baller"`, etc.) rather than raw enum values. There is no ADP anywhere in this app — it was removed (mock/meaningless) and shouldn't be reintroduced without a real source.

**Draft module** (`src/store/use-draft-store.ts`, `src/components/draft/`): `DraftRoomConfig` is set once via the room-config modal and gates the rest of the page — `DraftPage` conditionally *mounts* `RoomConfigModal` only while `config` is null (`{!config && <RoomConfigModal />}`), including after "Reset draft". This is deliberately mount/unmount rather than an `open`/`onOpenChange` prop driving Base UI's animated show/hide: the modal used to stay open via `<Dialog open={!config}>` while always being mounted, and relied on Base UI's exit-animation lifecycle to actually remove the popup from the page — which left the dialog visibly stuck on screen (config was updating fine underneath) in at least one real browser where the animation's end event apparently never fired. Unmounting the whole component the instant `config` is set sidesteps that class of bug entirely; `RoomConfigModal` itself just renders `<Dialog open>` unconditionally now since its own mount *is* the visibility toggle. Snake vs. auction is one config flag; `SnakeBoard` derives the on-the-clock team from `teamIndexForPick` (`src/lib/draft-logic.ts`, standard serpentine order), while `AuctionBoard` uses a nominate → award-pick flow. `BIG_BALLER_STARTUP_ROSTER` (2QB/4RB/5WR/2TE/2FLEX/2K/**25-man bench**, 4 teams, $600) lives in `src/lib/types.ts` — the "Big Baller Startup" preset button in the room-config modal applies it *and* sets `config.isBigBaller = true`. That flag (not a roster-shape comparison) is what tells `DraftPoolPanel` to use the Big Baller list regardless of the room's `scoring` dropdown — set explicitly by the preset button, and left as-is if the user hand-edits fields afterward, so it tracks intent rather than exact roster equality.

**The Draft board sources player order + auction pricing from whichever Rankings list matches the room, not raw `proj2026`.** `DraftPoolPanel` computes `const list: RankingsList = config.isBigBaller ? "BIG_BALLER" : config.scoring` (config.scoring is `PPR|HALF|STD`, which is exactly the non-Big-Baller subset of `RankingsList`) and reads `orders[list]` off `useRankingsStore`, passing it into `computeAuctionValues` (`src/lib/valuation.ts`) as `order`. So a Half-PPR snake room pulls your Half-PPR rankings, a Big Baller Startup auction pulls your Big Baller rankings, etc. — each independently. Internally, `reorderValuesByRank` takes the currently-available pool's own `proj2026` numbers, sorts them into a curve, and hands that curve back out in the order the user ranked those same players — so whoever they ranked #1 among what's left gets the pool's single highest number, *regardless of whose real projection it was*. `computeAuctionValues`'s `order` param is optional (falls back to raw `proj2026` if omitted) — every current caller passes it, so don't drop it when touching `DraftPoolPanel`, or dollar values silently stop tracking the user's rankings. Verified by promoting a different low-proj RB to #1 in each of the four lists independently, then confirming each of the four room types (PPR/Half/Standard scoring, and the Big Baller preset) surfaced exactly its own promoted player at the top of the pool.

**Dollar-value economics use one global replacement level, never one per position — this is deliberate, not simplified-away detail.** An earlier version of `computeAuctionValues` computed a separate VORP replacement level per position (Nth-best remaining player *at that position*, N scaling with roster config + a FLEX-share split across RB/WR/TE). That let a player at a structurally "scarce" position (e.g. QB, with few starting slots) outprice a player the user ranked *higher overall* at a "deeper" position — even though `reorderValuesByRank` already gave the higher-ranked player the bigger raw value, subtracting a taller position-specific baseline could still flip their VORP, and therefore their dollar value, in the wrong direction. Confirmed as a real, reproducible bug (not hypothetical): a synthetic pool with Josh Allen ranked #1 overall and Puka Nacua ranked #2 overall priced Puka Nacua at $293 vs. Josh Allen's $254 under the old per-position code — 12 rank-order inversions in one 26-player test pool. `computeReplacementLevel` (singular now) computes exactly one baseline for the whole pool — the value of the `teams × (roster.QB+RB+WR+TE+FLEX)`-th best skill player overall — and every player's VORP is `valueOf(player) - thatOneNumber`. Because `valueOf` is already monotonic in `order` (via `reorderValuesByRank`) and every player shares the identical baseline, the resulting dollar value is guaranteed non-increasing as rank gets worse, position included — a player can never be worth more than someone ranked above them, and since a tier is just a contiguous run within `order` (see the Rankings section above), tier boundaries are automatically respected too without needing separate handling. Kickers remain the one intentional exception: still flat-priced at $1 and excluded from both the replacement-level pool and the VORP pool, regardless of where the user ranked them. Don't reintroduce a per-position replacement level (or any other position-keyed step) into this path — that's exactly what caused the bug.

**Trade module** (`src/store/use-trade-store.ts`, `src/components/trade/`): the Compare tab is read-only (pick up to 3 players, highlight the better value per stat row). It has no list selector of its own — `comparison-table.tsx` and `trade-evaluator.tsx` both read `useActiveOrder()`/`useDisplayScoringFormat()`, so Trade reflects whichever of the four lists is currently open on the Rankings page. The DnD evaluator treats players/picks/FAAB as a flat `TradeAsset[]` with a `side: "A" | "B" | null`; `@dnd-kit/core`'s plain draggable/droppable (not the `sortable` variant used in Rankings) moves assets between three zones. Trade value for players comes from `tradePlayerValue` (rank + proj2026 + a static `POSITION_SCARCITY` multiplier in `src/lib/valuation.ts`) since the trade module has no draft-room roster context to derive scarcity from the way the auction engine does.

## Deferred (intentionally not built)

CSV import/export, right-click context menus, draggable column reordering, long-press mobile quick-actions, a light/dark toggle (it's dark-only right now). If asked to build on top of this, don't half-implement these — either build them properly or leave them out.

## Conventions

- Design tokens live in `src/app/globals.css` as CSS custom properties (`--pos-*`, `--status-*`, `--surface-muted`) layered on top of shadcn's default token set — reuse these rather than hardcoding hex values. There's a `:root` (light) and `.dark` block for every shadcn token plus the custom ones; the app forces `dark` on `<html>` in `layout.tsx` rather than exposing a toggle, but the light values are kept in sync in case that changes.
- The body font is Nunito, loaded in `layout.tsx` via `next/font/google` with `variable: "--font-sans"` — that exact name matters. It used to be Geist named `--font-geist-sans`, while `globals.css`'s `@theme inline` block separately declared `--font-sans: var(--font-sans)` (a self-reference, i.e. always invalid) expecting some other mechanism to define it — the two names never matched, so the whole app silently fell back to the browser's default serif font. If you swap fonts again, either name the font's `variable` exactly `--font-sans`, or reintroduce a *correct* (non-self-referential) mapping in `@theme inline` — don't add a `--font-sans` line to `@theme inline` pointing at itself again.
- shadcn/ui primitives are in `src/components/ui/` (this project's shadcn config uses the `@base-ui/react` based components, not Radix — check the existing primitive before assuming Radix-style props).
- Module-specific components are grouped under `src/components/{rankings,draft,trade}/`; cross-module pieces (position pill, empty state, nav) are in `src/components/shared/`.
